# セーブ構造の調査(2026-10-13)

調査と提案だけを行いました。コードもセーブも変更しておらず、動作確認(実行)もしていません。
パスは `Unity/2ndAction/Assets/Scripts/` からの相対です。

## 1. 現在の仕組み

- **保存先**: すべて PlayerPrefs です。Android では SharedPreferences(XML)、Windows ではレジストリに入ります。
  - ゲームのコードは `SaveStore` → `Platform.Save`(今は `PlayerPrefsStore`)を通して保存します(Platform/PlatformServices.cs:27-77, 101-115)。
  - 製品版のコードで PlayerPrefs を直接使っている所はありません(開発版専用の DebugPanel、CommitJournal の一部だけ)。
- **キーの登録表**: `SaveKeys.All` が全キーを Progress(進行)/ Settings(設定)/ Dev(開発用)/ Meta(管理情報)に分けています(Save/SaveKeys.cs:37-129)。
- **起動時の処理** `SaveSystem.Boot`(Save/SaveSystem.cs:38-143)は、次の順に動きます。
  1. 新規かどうかの判定
  2. 形式の移行(schema 0→3。移行前にファイルへバックアップし、失敗したら戻す)
  3. 製品版の世代(releaseGeneration)による初期化
  4. 検査と修復
  5. 確定の書きかけのやり直し(CommitJournal)
  6. `lastgood.json` の更新
- **バックアップ**: `persistentDataPath/SaveBackups/` に置いています。
  - lastgood / lastgood_prev(起動するたびに1世代ずつ回す)
  - pre_migration_*(形式の移行前)、release_reset_*(製品版の初期化前)、corrupt_*(壊れた値の退避)
- **端末の外への保存**: ランキングだけです(UGS の匿名サインイン。PlayerId が本人の識別)。Cloud Save と引き継ぎ機能はありません。進行は**端末の中だけ**にあります。

## 2. 確認できた問題

### 良くできている点(今のままでよい)

- **壊れた JSON**: corrupt_* に退避してから lastgood から戻し、戻せない時はその項目だけを初期値にします(SaveSystem.cs:263-274)。所持カード・Mastery・中断データは起動時に検査するので、「読めない → 空 → 上書き」になりません。
- **アプリの更新**: 移行の前にバックアップを取り、失敗したら元へ戻して旧形式のまま起動します(SaveSystem.cs:77-104)。新しい項目は、登録表の初期値と修復で補われます。
- **確定の途中で落ちた時**: 控えとまとめ書きで、欠けも二重書きも起きません(第3弾で強制終了 14 通りを試験済み)。
- **全部を消す処理**: `DeleteAll` の呼び出しはありません。初期化は開発版のパネルからだけです。

## 3. 今すぐ直したほうがよいもの

1. **A**(30分〜1時間)
   - PendingCommitV1 を登録表に入れ、製品版の初期化で控えも消します。
   - 試験を1件追加します。
2. **B と C**(合わせて2〜3時間)
   - 新規扱いになった時に、バックアップに進行が残っていれば上書きしません。別名で残し、自動で戻すかどうかは要相談です。
   - バックアップは一時ファイルに書いてから置き換えます。
   - lastgood が読めない時は prev を使います。
   - 起きる頻度は低いものの、起きると全部を失うので、公開前に直しておく価値があります。

D と E は影響が小さいため、余裕があればでかまいません。

### 公開前に決めておくこと(不具合ではありません)

- **会社名・製品名・パッケージ名** `companyName: DefaultCompany` / `com.zero0084.action2nd`(ProjectSettings.asset:15-16, 171-172)
  - 保存先はこれらの名前で決まります。公開した後に変えると、今のセーブを読めなくなります。
- **署名の鍵** `androidUseCustomKeystore: 0`(今は debug の鍵)
  - 公開した後に鍵を変えると上書きで更新できず、アンインストールが必要になってセーブが消えます。
- **Android の自動バックアップ** `allowBackup`
  - マニフェストに指定がなく、Android の既定では有効です。今ある唯一の「機種変更で戻る」経路ですが、設計して使っているものではありません。使うか止めるかを決めておくのがよいです。

## 4. 他機種へ展開する時まで後回しにできるもの

- **引き継ぎ・クラウド**: 今はありません。
  - 土台として、`SaveSystem.Capture()` で登録済みの全キーを型付きの JSON にできます。Progress と Meta だけに絞れば、書き出しの元にできます。
- **共有する進行と端末ごとの設定の分け方**: 登録表の分類がそのまま使えます。
  - Settings: ほぼ端末ごと。
  - Progress と Meta: 共有。
  - 例外: ランキング・広告の回数・パスは、本人やストアのアカウントに結び付く扱いが必要です。
- **ランキングの本人**: UGS の匿名 ID です。再インストールや機種変更で別のプレイヤーになります。各機種のアカウント連携で直す方針です(OnlineServices.cs:25)。
- **購入**: ストアのアカウントごとです。Google Play で買ったものは iPhone や PC へ移りません。機種をまたぐには、自前のアカウントと権利の管理、各ストアの規約の確認が必要です。
- **PC**: レジストリはファイルではないため、ファイルに保存する `ISaveStore` を足すのが自然です。
  - バックアップなどは `persistentDataPath` に直接書いているので、そこも抽象化が必要です。
  - 保存の差し替えとセーブの起動処理が同じタイミング(`BeforeSceneLoad`)で、実行される順番が保証されていません(PlatformServices.cs:136-141、SaveSystem.cs:38)。
- **PS・Switch**: 保存の API、容量、書き込み中の表示などの要件は、公開されていない仕様と契約に関わります。**推測せず、別途の確認が必要です。**
  - コード側の準備として、保存の抽象化をファイルや非同期にも広げることが課題になります。
- **同じセーブを2台で使う不正(MILE の複製)の対策**: 一方向の移行にする、移行元を無効化する、などが考えられます。
