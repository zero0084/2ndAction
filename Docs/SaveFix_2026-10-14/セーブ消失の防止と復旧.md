## 1. 変更内容

### A: 確定の控えのキー管理と、製品版の初期化との順番
- 確定の控え `PendingCommitV1` を、キーの登録表に「進行」として入れました(Save/SaveKeys.cs:55)。
  - 製品版の初期化(③)は進行のキーをすべて消すので、控えも一緒に消えます(Save/ProgressStats.cs:201-204)。
  - 控えの中身は、初期化前のバックアップ(release_reset_*.json)に残ります。
- **起動時の順番:**
  1. ⓪ 消失の確認
  2. ② 形式の移行
  3. ③ 製品版の初期化
  4. ④ 検査と修復
  5. ⑤ 控えのやり直し
  6. バックアップの更新
- 初期化(③)が控えのやり直し(⑤)より先に動きます。⑤ の時点では控えが消えているので、開発版の BEST・解放・MILE は戻りません。
- **念のための二重の防止:** 控えに「書いた時の世代」を持たせました。今のデータより古い世代の控えは反映せず、`discarded_journal_gen*.txt` に残して捨てます(Save/CommitJournal.cs:63)。同じ世代の控えは、今までどおり反映します。

### B: 保存データが消えて、バックアップだけ残った場合
- 起動の一番最初(何も書く前)に確認します。進行のキーが1つも無いのに、進行の入った正常なバックアップが残っていれば、そこから戻します。
  - 戻す順は「最新 → 1つ前」です。
  - 戻した値はすぐ保存するので、その後で落ちても戻した状態から始まります(Save/SaveSystem.cs:70-87)。
- 設定のキーが残っていれば、今の値を優先します(控えより新しいため)。
- 戻した時は、ホームで「OK」を押すまで残るお知らせを出します。戻した控えの日時と「この時点より後の進行は含まれていない場合があります」を書いています(30言語)。
- 戻せるバックアップが無い時は新規開始になります。その時も、残っているバックアップのファイルは `orphan_<日時>_lastgood*.json` に移して残します。空の状態で上書きしません(Save/SaveSystem.cs:561)。

**正当な新規開始・初期化と、データ消失の区別**

| 状態 | 保存データ | バックアップ | 結果 |
|---|---|---|---|
| 新規インストール / アンインストール後 / Android の「ストレージを消去」 | 無い | 無い(アプリのフォルダごと消える) | 新規開始 |
| 保存データだけが消えた / 読めない | 進行のキーが無い | 正常な物がある | **バックアップから戻す** |
| 保存データが消え、バックアップも壊れている | 進行のキーが無い | 壊れている | 新規開始。壊れたバックアップは orphan_* として残す |
| 開発用の全初期化(DEBUG) | 消す | 先に `dev_reset_all_*` へ移す | 新規開始(戻らない) |
| テスト用データの消去(DEBUG) | テスト用だけ消す | テスト用のフォルダごと消す | 新規開始(戻らない) |
| 製品版の初期化(③) | 進行を初期値に書き直す(キーは残る) | release_reset_* に残す | 初期化(B の対象外) |
| 普段の起動 | 進行のキーがある | – | 今までどおり |

- 一度でも起動したセーブは、必ず進行のキーを持っています(新規開始の時に MILE などの初期値を書くため)。そのため「進行のキーが1つも無い」状態は、消失か意図した初期化の時にしか起きません。

### C: バックアップの書き込み
- バックアップは一時ファイル(`*.json.tmp`)に書き切り、ディスクへ書き出してから、元のファイルと置き換えます(Save/SaveSystem.cs:469)。
  - 置き換えが使えない環境では「消してから移す」に切り替えます。その場合も、もう一方の世代が残ります。
- **世代の回し方**(どこで落ちても、正常な控えが少なくとも1つ残る順番。Save/SaveSystem.cs:587):
  1. 最新を 1つ前へ回す
  2. 新しい最新を書く
- 最新が壊れていた時は、壊れた物を1つ前へ回しません(1つ前を守る)。壊れた最新は `corrupt_lastgood_<日時>.json` として残します。
- 修復(壊れた項目を戻す時)も、最新が読めなければ1つ前を使います。

### ついでに直したもの
- **開発版の検証用のメモリ保存(-memSave)**
  - これまで: バックアップのファイルだけは、このPCの本物の保存先へ書いていました。全キャラ検証のように8本同時に動かすと、本物の `lastgood.json` が試験の状態で上書きされていました。B の「バックアップから戻す」と組み合わさると危険です。
  - 直した後: プロセス専用の一時フォルダに書きます(開発版だけの処理。Save/SaveSystem.cs:439)。
- **開発用の全初期化**: 初期化の前にバックアップを別名へ移すようにしました(戻ってしまわないように)。

## 3. 実機での確認の手順(マスターへのお願い)
APK 305 を入れて行ってください。普段のデータは使わず、DEBUG の「テスト用データ」に切り替えて行います。

**A. 普段のデータが消えないこと(まず最初に)**
1. APK 305 を上書きで入れます(アンインストールしない)。
2. 起動して、いつもの BEST・MILE・カード・解放がそのまま残っていることを確認します。
3. 「セーブデータの復旧」のお知らせが出ないことを確認します(普段のデータは消えていないため)。

**B. 消失からの復旧(テスト用データで。USB デバッグと adb が必要)**
1. DEBUG → テスト用データ(新しく作る)に切り替えます。1回ランを走って脱出し、MILE と BEST を作ります。
2. アプリを完全に終了して、もう一度起動します(ここでバックアップが取られます)。この時の MILE・BEST を控えておきます。
3. アプリを完全に終了し、PC から次を実行します。
   ```
   echo -srLoseAtStart > qa_args.txt
   adb push qa_args.txt /sdcard/Android/data/com.zero0084.action2nd/files/qa_args.txt
   ```
4. アプリを起動します。
   - 期待: ホームで「セーブデータの復旧」のお知らせが出て、MILE・BEST が 2. の値に戻る。
5. もう一度、完全に終了して起動します。
   - 期待: お知らせは出ず、値はそのまま。
6. (任意)最新のバックアップが壊れた場合を試すには、3. の中身を `-srLoseAtStart -srCorrupt lastgood` にします。
   - 期待: 1つ前のバックアップ(5. より前の起動の時点)から戻る。
7. 終わったら、DEBUG → 通常のデータに戻します。

- qa_args.txt は1回読むと消えるので、次の起動には効きません。
- これらの引数はテスト用データの時しか効きません。通常のデータの時は何もしません。

**C. 正当な新規開始(普段のデータを消したくない場合は、この項目は省略してください)**
- Android の設定 → アプリ → ストレージを消去 → 起動。
- 期待: 新規開始。復旧のお知らせは出ない(バックアップも一緒に消えるため)。
