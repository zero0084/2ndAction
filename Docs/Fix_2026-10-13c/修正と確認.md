## 1. オート補助のフレームレート依存

### 撮影の影響と低い fps の影響の切り分け
- 撮影(動画の書き出し)は `Time.captureFramerate = 30` で、ゲームを 1/30 秒ずつ進める。描画が 30fps の端末と同じ「1フレームが長い」状態になる。撮影そのものが補助を遅くするのではなく、**1フレームの長さ**が原因
- 撮影なしで `-blFps 30` / `-blFps 60` を同じキャラ・構成・地形・乱数(種)で比べた(メカドラゴン戦、ラスダン 60km の関門、育成済み)

| | 30fps | 60fps | 差 |
|---|---|---|---|
| 直す前: 格闘家 D 撃破時間 | 299.0秒 | 248.6秒 | 30fps が 20% 遅い |
| 直す前: 格闘家 D 攻撃/秒 | 2.66 | 2.89 | 30fps が 8% 少ない |
| 直す前: 拳銃士 A | 倒れた | 44.3秒で撃破 | |
| 直した後: 格闘家 D 撃破時間 / 攻撃/秒 | 259.8秒 / 2.91 | 221.5秒 / 2.99 | 攻撃の差 3% |
| 直した後: 黒剣士 D 撃破時間 / 攻撃/秒 | 198.3秒 / 2.31 | 257.5秒 / 2.30 | 差なし(撃破は 30fps の方が早い) |
| 直した後: 拳銃士 A 攻撃/秒 | 3.64 | 3.66 | 差なし |

(直した後の 60fps 側は同時に動かした試験の負荷で実際は 40〜50fps。直す前は 57fps)

### 見つけた fps 依存と直し方
1. **攻撃の間隔**(影響が最大): 補助は攻撃の待ち時間を「このフレームで減る前の値」で見ていたため、毎回 1 フレーム遅れて押していた(30fps では 33ms、60fps では 17ms)→ 減った後の値で判定
2. **跳ぶ高さ**: 1フレームずつ「速度を減らしてから位置に足す」計算で、fps が低いほど頂点が低かった(9m/s の跳躍で 60fps と 30fps の差 約 0.08m)→ 60fps の時と全く同じ軌道を、どの fps でも出す式に変更(手動の操作も同じ。60fps の動きは今までと同じ)。補助の先読みも同じ式
3. **ボスの攻撃の回避の踏み切り**: 1.5 フレーム前に跳んでいた(fps が低いほど早く跳ぶ)→ いちばん近いフレームで跳ぶ
4. **踏み切り予定の探し直し**: 4フレームごと → 時間で(60fps の 4 フレーム分)
- 一時的なフレーム落ち: 20フレームごとに 80ms 止める試験で、1フレームに始まった攻撃は最大 2(止めない時も 2 = 二丁拳銃/連撃の追加。まとめ出しは起きない)。入力は1フレームに1つだけで、重複しない

## 2. 攻撃・回避・穴ジャンプの競合(共通の補助処理)
- 原因: ボス戦の補助の「ボスへ跳ぶ」「攻撃を跳んで避ける」「空中の二段で避ける」は、着地の場所を見ていなかった。地形の補助が「この後跳ぶ予定/着地してから跳ぶ予定」の時でも、ボスの理由の跳躍が先に出て穴に落ちる/穴のために残していた二段ジャンプを使い切っていた
- 直し方: ボスの理由で跳ぶ前に、**地形の補助と同じ先読み**(足場・着地の位置・残りのジャンプ回数・天井・天井の針・障害物・着地の後の余裕)で「今跳んだら安全に着地できるか」を確かめ、危ない時は跳ばない(必要なら後の二段も含めて試す)。メカドラゴンだけでなく全ボス共通
- 天井から攻撃が来る時(低くいる)でも、跳ばないと穴に落ちる踏み切りは跳ぶ(以前は跳ばずに確実に落ちていた)
- 個別の設定: 自動攻撃 OFF / 自動回避 OFF の判定を、優先を決める前にそれぞれの操作に掛ける(以前は OFF の側の操作に負けた方の操作まで消えていた)。ボス戦での確認: 自動攻撃 OFF → 補助の攻撃 0・回避は出る / 自動回避 OFF → 補助の跳躍 0・攻撃は出る / ボス戦オート OFF → (下の表)。手動の操作が補助より優先されるのは今までどおり
- 確認(メカドラゴン戦、同じ種): 穴への落下 格闘家 D 4〜6 → 0〜2、黒剣士 D 7 → 0〜4。安全でないため取りやめたボスの理由の跳躍 1戦 2〜16回

## 3. 成功の確定の途中で終了した時
- 直す前: 確定の印を先に書き、その後 MILE/BEST/解放/投稿待ちを別々に保存していた。**印の保存の後、MILE を書く前に落ちると MILE を失い、印があるので二度と確定し直せなかった**(二重の反映は無かった)
- 直し方: 確定の前に「控え」(MILE/累計距離の書く前と後の値、BEST、解放、投稿、ランの ID)を保存 → 確定の書き込みを1回の保存にまとめる → 控えを消す。起動時に控えが残っていれば、まだ書いていない物だけを書く(MILE と累計距離は「書く前の値と一致する時だけ書いた後の値にする」ので二重にならない)
- 検証(テスト用データだけ。実際にプロセスを強制終了して再起動): 確定の7か所 × 2通り(落ちる前に書き出す/書き出さない)= 14通りすべて合格
  - 控えを書く前に落ちた → 何も確定していない・中断データから再開できる → 脱出で1回だけ確定
  - それ以外(控えの後/確定の印の後/MILE の後/中断データの削除の後/保存の直前/保存の直後)→ MILE はちょうど1回・BEST・累計距離1回・解放・投稿待ち 1件・中断データから再開できない(二度目の報酬なし)・もう一度起動しても何も増えない
